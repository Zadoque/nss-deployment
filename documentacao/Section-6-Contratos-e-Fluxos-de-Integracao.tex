\section{Contratos e Fluxos de Integração}

A existência de três repositórios exige contratos claros. O objetivo é permitir que cada componente evolua sem criar dependências implícitas entre implementações internas.

\subsection{Contrato frontend--Java}

O frontend consome exclusivamente a API pública do Java. O contrato deve definir:

\begin{itemize}
    \item endpoints;
    \item parâmetros e filtros;
    \item formato das respostas;
    \item códigos HTTP;
    \item mensagens de erro;
    \item paginação, quando aplicável;
    \item requisitos de autenticação e autorização.
\end{itemize}

\subsection{Contrato Python--PostgreSQL}

O pipeline e o Java compartilham o PostgreSQL. O schema do banco funciona, portanto, como um contrato de integração interno.

As mudanças de schema devem ser versionadas por migrations e acompanhadas de análise de compatibilidade com o backend Java.

\begin{regra}[Compatibilidade de schema]
Uma alteração no PostgreSQL não deve ser publicada apenas porque o pipeline consegue executá-la. Deve-se verificar se as consultas e mapeamentos utilizados pelo Java continuam válidos.
\end{regra}

\subsection{Fluxo de consulta}

\begin{lstlisting}[language=Mermaid]
sequenceDiagram
    participant U as Usuário
    participant F as Frontend
    participant J as Java
    participant D as PostgreSQL

    U->>F: Interage com a aplicação
    F->>J: Requisição HTTP
    J->>J: Autenticação / autorização
    J->>D: Consulta
    D-->>J: Dados
    J-->>F: DTO / JSON
    F-->>U: Visualização
\end{lstlisting}

\subsection{Versionamento}

Recomenda-se que contratos importantes sejam documentados e, quando possível, verificados automaticamente. A API Java pode utilizar OpenAPI para manter uma especificação formal de seus endpoints.
